  一、先用一句话总结：对你来说，什么是 skill？

  可以把 skill 理解成：

  ▎ 一张可复用的「说明卡」，专门用来规定：
  ▎ AI 在某一类任务上，要用什么风格、遵守什么规则、避免什么行为。

  特点：

  - 不是一次性的 prompt，而是可以反复拿出来用的「模块」
  - 不负责完成具体功能，而是控制怎么做、做成什么风格
  - 可以多张卡一起用：比如「极简 UI 审美」+「前端工程习惯」+「中文回答风格」

  你最后要拥有的是：整盒自己的「说明卡」，而不是一张卡。

  ---
  二、skill 能做什么？（不只 UI）

  你现在主要是 UI 方向，但 skill 能管的范围其实更广，大概有几大类：

  1. 审美 / UI 风格类
    - 定义界面配色、图标风格、圆角阴影、布局气质
    - 比如：
        - 极简商务、低饱和、不用 emoji
      - 柔和蓝灰首页风格
      - 暖色生活类 H5 风格
  2. 代码习惯 / 工程规范类
    - 告诉 AI 写代码时要遵守哪些工程规则
    - 例子：
        - 组件拆分原则、文件命名、目录结构
      - API 调用统一放 service 层，错误统一处理
      - 优先写类型安全代码，避免 any
  3. 工作流 / 思考方式类
    - 规定做事顺序和思考框架
    - 例子：
        - 「先问清需求 → 画结构 → 再写代码」
      - 「先给总览，再给细节，再给可选方案」
      - 「遇到不确定的地方先提问，不乱猜」
  4. 输出风格 / 语言习惯类
    - 控制回答的口吻、结构、语言
    - 例子：
        - 中文简洁表达，不废话
      - 输出结构固定：概览 → 要点 → 代码 → 注意事项
      - 错误时直说不知道，不瞎编

  你未来可以为每一类都写自己的 skills，而不仅限于 UI。

  ---
  三、一个 skill 里面通常包含什么？

  最小版本，其实只需要几块信息：

  1. 名称
    - 要一眼看懂用途，比如：
        - ui/base-minimal-business
      - code/frontend-structure-react
      - lang/zh-concise-answer
  2. 目标（1–3 句）
    - 这张卡是干嘛的，要把 AI 拉成什么样子
    - 比如：
        - “让 UI 保持极简商务风，避免廉价 AI 样式。”
  3. 适用范围
    - 什么时候用、什么时候不用
    - 比如：
        - “当你设计 Web / PC 端 UI 时默认启用；移动端另外有 skill。”
  4. 核心原则 / 行为规则
    - AI 做这类事时应该怎么做
    - 比如 UI skill 会写：配色、间距、排版、图标风格
    - 代码 skill 会写：目录结构、命名、错误处理方式
  5. 禁用项（Hard NO）
    - 你坚决不要看到的东西（很重要）
    - 比如：emoji 图标、彩虹渐变、随便造字段名等

  这 5 块就是 skill 的“主身体”，已经足够让 AI按这个风格来。

  ---
  四、skill 的扩展：可以做到多强？

  在上面基础上，你可以慢慢给 skill 增肌：

  1. 配置项（让 skill 可调）
    - 比如 UI skill：
        - primaryColor：主色（但仍要求低饱和）
      - density: comfortable / compact

    - 这样同一个 skill 可以在不同项目换参数，而不是重写一套。
  2. 模板 / Snippets
    - UI skill 附带一些典型布局模板（Hero + 卡片 + 列表），
  代码 skill 附带常用函数/组件骨架。
    - 用的时候可以说：“按这个 skill 的风格生成一个新的页面/组件。”
  3. 脚本 / 校验工具（进阶）
    - 比如 UI skill 附一个脚本检查 CSS 有没有高饱和渐变、太大圆角。
    - 代码 skill 附一个脚本检查目录结构是否符合约定。
  4. 示例 / Demo
    - 每个 skill 附一个小 demo：
        - 1 页 UI 或 1 段代码，展示“用这个 skill 写出来大概长这样”。

    - 以后你自己看也好记：这个 skill 的效果是什么。

  你现在阶段，先干干净净写「文字 rules」就足够，其他都可以以后慢慢加。

  ---
  五、设计你个人 skills 体系时，可以遵守的几条总规则

  这部分是我建议你“写任何 skill 都遵守”的 meta 规则：

  1. 单一职责
    - 一个 skill 只解决一个维度的问题：
        - UI 审美基因、
      - 某个主题、
      - 某个平台、
      - 代码风格、
      - 输出语言风格……

    - 不要把所有东西塞在一个 skill 里。
  2. 可组合
    - 想象你在用的时候，会说：
    ▎ 「启用：A（基础审美） + B（主题） + C（平台） + D（代码习惯）」
    - 所以每个 skill 要写清楚“可以和谁一起用，不要重复规定同一件事”。
  3. 抽象，而不是像素级
    - 多讲“气质、禁用项、倾向”，少讲“某按钮宽度 120px”。
    - 这样 skill 才能跨项目、跨端复用。
  4. 显式写出硬约束 vs 软偏好
    - 硬约束：绝不允许（例如「禁止 emoji 图标」）。
    - 软偏好：优先这样，但用户特别要求时可以妥协。
    - 在 skill 里用词区分开（比如 MUST / SHOULD）。
  5. 与具体项目解耦
    - 基础 skill 里不要写「个人财务系统」「某个公司名」。
    - 项目特有东西放到「项目 skill」里去。

  ---
  六、针对你现在的情况，我建议的起步方案

  你现在已经有：

  - 一些 UI 方面的想法（极简、蓝灰、去 AI 味）；
  - 一些对 skill 抽象程度的直觉（不要太具体）。

  我建议我们这样一步步来：

  1. 先定 3 大类你最想要的 skills 方向
  举例，你可以选：
    - A. UI 审美 / 视觉风格类
    - B. 前端代码结构 / 组件习惯类
    - C. 回答方式 / 语言风格类

  2. 我们先为每一大类写一个“Base Skill 轮廓”（只写纲要，不细节）
  比如：
    - ui/base-minimal-business：极简商务 UI 基因（我们已经差不多成型了）；
    - code/base-frontend-clean：统一前端工程习惯；
    - lang/zh-concise：中文表达简洁、不废话。
  3. 等这 3 个“Base 轮廓”稳定了，再在每一类下面长分支
    - UI 下再长：蓝灰首页、纯后台表格、小程序轻量风…
    - code 下再长：React 模式 / Vue 模式 / 接口层模式…
    - lang 下再长：写文档模式 / 写注释模式 / 写 commit message 模式…

  你真正想要的是：
  ▎ “以后我做任何东西，只要挑几张我写好的 skill 卡片给 AI 看，它就像一个懂我喜好的合作伙伴。”     

  ---
  七、下一步怎么一起写？

  接下来可以选一个方向作为「第一个真正写完的 skill」：

  - 要么继续完善 UI 基础审美 skill（现在已经有雏形，很贴近你财务首页这套）；
  - 要么从零设计一个 前端工程习惯 Base Skill，比如规定：
    - 文件命名方式、组件拆分原则、接口封装习惯、错误处理优先级…

  你选一个方向，我就用“带你一起写”的方式：先给骨架，再一起填内容，这样你会对「如何写
  skill」有手感，而不是只停在概念上。
